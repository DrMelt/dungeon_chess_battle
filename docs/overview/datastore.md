# 状态存储域内部机制

覆盖 `Server.DataStore.Shared`（存储契约与快照模型）与 `Server.DataStore`（进程内实现，当前唯一实现基于 `ConcurrentDictionary`）。模块边界见 `functional_boundary/10`、`11`；大厅侧「身份只从登录会话反查」的业务约束见 `overview/lobby`；归档的录制与查询两端见 `flow/replay-design`；对外端口的契约归 `Server.Abstractions`，见 `overview/server`。

## 契约与所有权

- 门面 `IGameStateStore` 组合 `IRoomStateStore`（房间级）与 `IPlayerStateStore`（玩家级），业务层只面向门面，存储引擎在装配层替换。并发语义写在契约上——任何线程都可调用，同房间读改写由实现保证原子；换实现必须兑现同一句话。
- 三份实现同居本层：房间与玩家状态 `InMemoryGameStateStore`、回放归档 `InMemoryReplayStore`、身份解析 `PlayerIdentityResolver`（适配器，包在门面之上）。归档与身份解析的契约不进 `DataStore.Shared`——大厅不认识回放与 HTTP 端点，这两个端口只由服务端契约层承担。
- 校验落在存储而非业务：已准备不可改单位、未选单位不可准备、房主不参与准备判定、登录名空或超 `PlayerName.MaxLength` 直接拒绝不降级（降级会让身份名与显示名漂移）。调用方重复实现同一判据就是分叉的开始。
- 全员就绪判定的兜底方向是更严：无房主记录时 `IsAllOthersReady` 退化为全部成员都需就绪，而不是全部放行。
- 不入本模型的东西：网络连接密钥（属网络层）、战斗房间会话（属房间私有）、战斗单位状态（由领域 `BattleUnit` 权威持有）、归档内容与摘要（归 `Replay.Shared`）。

## 锁与快照

- 房间级锁表 `GetRoomLock`：每房间一个常驻锁对象，串行化同房间读改写，保护 `List<T>` 操作与可变模型字段。条目不随房间删除回收——回收会让新旧锁错位竞态，房间数量有限，留下旧锁可接受。
- 三类读不持锁：跨房间枚举（逐房间取锁会引入多锁顺序死锁，依赖 `ConcurrentDictionary` 弱一致性快照，字段可能略旧可接受）、单条目 `TryGetValue`（连接归属仅作身份校验）、登录会话与玩家记录表（单条目操作本身原子）。
- 锁外定位、锁内重确认：`RemovePlayerByConnection` 先在锁外读归属，只为拿到该用哪把锁，进锁后重新 `TryRemove` 取实际读数——连接可能已在两步之间被改归到别的房间，按旧读数清理会漏掉新归属。
- 单锁内完成登记：`TryRegisterRoomWithHost` 在一次加锁内做完注册、子表初始化、房主登记、连接归属与 playerId。「注册后再取一次锁登记房主」的写法，两步之间房间可能已被并发移除。
- 对外读一律返回深拷贝（`CloneRoom`、快照、新建集合），阻止调用方绕过房间锁改写 Store 内的可变对象。
- 房主名是派生双写字段：房主表与 `GameRoom.HostName` 必须同锁内一起更新。不同步的表现是招募板显示旧房主、而房主判定与成员登记用新房主。
- 快照组装不抛也不返回 null：房间已不存在时 `GetRoomState` 给出空快照，副本键原样取出（缺失为空串），默认副本兜底归大厅广播组装点 `ResolveDungeonKey`——广播组装点因此不需要为并发删房做判空。

## 身份与会话凭证

- 三张表三条键向：登录会话 `connectionId → 登录名`（服务端权威身份）、会话凭证双向登记 `凭证 → 登录名` 与 `connectionId → 凭证`（前者供 HTTP 侧解析，后者供换发与撤销）、玩家记录注册表 `登录名 → 主键`。
- 换发即撤销：一条连接同时最多一条有效凭证，不留双活身份；撤销随登录会话移除一并完成——连接都没了，HTTP 侧不该还留着身份。
- 玩家记录注册表进程内只增不删，名字首次出现即分配主键。同名玩家共享主键导致回放互见，属已知局限。
- 解析为「凭证 → 登录名 → 主键」两步查表；凭证无效或所属连接已登出时返回 null 且不登记记录，避免匿名凭证凭空建出主键。
- 凭证与主键都不跨进程重启：重启后同名玩家派生新主键，旧主键只残留在客户端本地副本里，不再可比。

## 成员移除与停机清理

- 成员移除按房间阶段分家：Waiting 执行人数扣减、准备单位清理与房主转让（转给剩余成员，无剩余则移除房主记录），最后一人退出删除房间全部状态并返回 null 通报调用方无需广播；InProgress 只做基础清理，房间生命周期归 `BattleRoomManager`。
- 基础清理（准备状态、playerId 映射、准备单位）任何阶段都执行，不留状态残留；人数扣减与删房只在 Waiting 做，InProgress 的房间何时销毁由 `BattleRoomManager` 单方面决定。
- `RemoveRoomState` 清房间六张表并在同一把房间锁内遍历清该房间的连接归属，与 `RegisterRoomPlayer` 互斥——否则可能删掉刚登记进去的归属。
- `ClearAllState` / `Dispose` 只在停机流程调用，前提是所有房间线程已 Join：此时不存在并发写入，才允许不加锁地整表清空。锁表一并清空，停机后不再有房间，旧锁对象无保留价值。

## 回放归档存储

- 三个结构共享一把库级锁：`roomId → (归档字节, 参与者记录主键)` 主表、`记录主键 → 房间列表` 反向索引、插入顺序表。三者必须同锁变更，否则淘汰会留下悬空索引条目；归档只发生在房间销毁与关服流程，写入频率不值得按房间拆锁。
- 保留最近 `MaxReplays = 256` 场，按插入序淘汰；反向索引按被淘汰归档自己记录的参与者清理，与新入库的那场无关。
- 同一 `roomId` 重复写入直接忽略：覆盖会让旧参与者的索引条目无人清理，顺序表也会把一场计两次。
- 检索按索引倒序（最新在前）返回，并过滤主表中已不存在的房间 ID——索引与主表一旦不同步，读取侧兜底而不是抛错。
- 摘要不入库，读侧从归档元数据块现取：同一份事实不留两个落点。
- 归档与索引同样只在进程内，重启即全清；换成磁盘或对象存储实现时，替掉的是本层，读写两端不动。
